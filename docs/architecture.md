# Архитектура

Как устроен код. Приложение это примерно 7800 строк Python, тесты ещё около 8800 строк.

## Общая схема

Обычное приложение на discord.py 2.7 с префиксными командами. Точка входа - `main.py`, дальше два расширения предметной области (`tickets`, `afk`), слой данных (`database`) и общие утилиты (`utils`).

```
src/app/
├── main.py              - точка входа: интенты, lifecycle, обработчик ошибок команд
├── config.py            - настройки, тексты, разбор .env и валидация
├── requirements.txt     - runtime-зависимости с хешами
├── .env.example
│
├── database/            - слой данных на sqlite3
│   ├── db.py            - соединение, WAL, отдельный поток для SQLite, retry на busy
│   ├── schema.py        - каноническое описание таблиц, индексов и статусов заявки
│   ├── migrations.py    - версии схемы, preflight, бэкап перед миграцией
│   ├── tickets_db.py    - таблицы tickets и stats, переходы статусов, связь с логами
│   ├── afk_db.py        - таблицы afk_users, afk_cooldown, afk_stats
│   └── state_db.py      - key-value bot_state: ID объектов, созданных ботом
│
├── tickets/             - заявки
│   ├── commands.py      - !famqcore, !stats, !history, !delete_user_data, панель заявок
│   ├── create_ticket.py - форма TicketModal и создание тикета
│   ├── decision.py      - кнопки «Принять» и «Отказать»
│   ├── close_ticket.py  - кнопка «Закрыть тикет»
│   ├── call_voice.py    - кнопка «Вызвать на обзвон»
│   ├── workflow.py      - общий сценарий терминального действия над заявкой
│   ├── transcript.py    - снимок переписки перед удалением канала
│   ├── reconcile.py     - фоновая сверка: заявки без каналов, зависший processing
│   ├── retention.py     - фоновое удаление заявок старше срока хранения
│   ├── erasure.py       - удаление персональных данных участника
│   └── views.py         - FullTicketView, собирает четыре кнопки тикета
│
├── afk/                 - AFK
│   ├── commands.py      - !afk, !afk_list, !afk_check, !afk_stats, !afk_remove
│   ├── views.py         - меню, форма ухода, подтверждение возврата, список AFK
│   ├── duration.py      - разбор «2 часа», «23:45», «1 ч 30 мин»
│   ├── models.py        - сессии, ники, длительности, статистика
│   ├── events.py        - автоответ на упоминание AFK-участника
│   └── tasks.py         - фоновое снятие истёкших AFK и уборка кулдаунов
│
└── utils/
    ├── clock.py         - единый источник времени, UTC в базе, пояс сообщества для ввода
    ├── errors.py        - error boundary, correlation id, повтор временных ошибок Discord
    ├── logger.py        - консоль и файл с ротацией
    ├── logcenter.py     - приватный лог-центр, проверка приватности, fail closed
    ├── mentions.py      - политика AllowedMentions и экранирование пользовательского текста
    ├── permissions.py   - единая проверка прав модератора
    ├── ratelimit.py     - in-memory лимитер с ограниченной памятью
    ├── resolve.py       - поиск объектов строго по ID
    └── startup.py       - проверка инфраструктуры сервера после подключения
```

Тесты лежат в `src/app/tests/`, группы задаются в `tests/run_suite.py`.

## Что происходит при старте

1. `main()` проверяет конфигурацию (`config.validate`). Если есть проблемы, бот печатает их списком и завершается с кодом 1, не подключаясь к Discord.
2. `setup_hook()` создаёт или мигрирует схему, загружает расширения `tickets` и `afk`, регистрирует persistent views.
3. Расширения поднимают свои фоновые Cog'и: снятие истёкших AFK, ретенция заявок, сверка состояний. Все они стартуют после `wait_until_ready` и отменяются в `cog_unload`.
4. На первом `on_ready` запускается `check_startup`: проверка всех заданных ID на каждом сервере (роли, категория, голосовые каналы, лог-центр и его приватность). В production любая проблема останавливает бота, в режиме `ALLOW_NAME_FALLBACK` это просто предупреждения.

## Поток заявки

```
!famqcore -> панель TicketTypeView (кнопки RP/CAPT)
          -> проверка «нет ли уже открытой заявки» -> TicketModal (5 полей)
          -> создание: роль -> личка -> категория -> приватный канал -> запись в БД
          -> в канале FullTicketView, адресный пинг рекрутёрских ролей
          -> запись в ветку 📝-заявки, ID сообщения сохраняется в tickets.log_message_ids
          -> «Принять»/«Отказать»/«Закрыть» -> захват заявки (processing)
          -> транскрипт -> запись в лог-центр -> финальный статус и дневная статистика
          -> удаление канала
```

Порядок шагов в конце один и тот же для всех трёх терминальных действий, он зафиксирован в `tickets/workflow.py`. Смысл такой: сначала сохраняем данные, только потом удаляем канал. Если Discord отказал на середине, заявка возвращается в `open` и действие можно повторить.

## Поток удаления персональных данных

```
!delete_user_data @user -> подтверждение кнопкой (работает только для вызвавшего админа)
        -> удаление каналов открытых тикетов
        -> удаление связанных сообщений лог-центра вместе с транскриптами
        -> анонимизация записей tickets и удаление AFK-данных, ник возвращается
        -> запись в ветку 🧾-аудит: ID админа, ID субъекта и счётчики
```

## Поток автоответа AFK

```
on_message -> собираем до 5 уникальных упоминаний (без ботов и автора)
           -> один запрос в БД: кто из них в AFK
           -> лимит канала (3 ответа за 20 секунд)
           -> резерв кулдауна по паре «упомянувший - AFK» (30 секунд)
           -> один общий ответ в канал, удаляется через 60 секунд
```

Обработчик зарегистрирован как `Cog.listener`, поэтому он не мешает обработке команд.

## База данных

Один файл SQLite: `src/app/database/database.db`. Режим WAL, `row_factory = sqlite3.Row`, все запросы идут через выделенный поток на путь к базе, так что гонок между задачами нет. Временные ошибки (`database is locked`) повторяются с backoff. Версия схемы хранится в `PRAGMA user_version`, актуальная - 4.

### tickets

| Колонка | Тип | Комментарий |
|---|---|---|
| `id` | INTEGER PK AUTOINCREMENT | |
| `guild_id` | INTEGER | ID сервера, все выборки идут через него |
| `channel_id` | INTEGER UNIQUE | Ключ поиска тикета по каналу |
| `user_id` | INTEGER | ID заявителя, `0` после анонимизации |
| `user_name` | TEXT | Имя на момент подачи |
| `topic` | TEXT | Заголовок формы |
| `type` | TEXT | `rp` или `capt` |
| `answers` | TEXT | JSON с ответами формы |
| `status` | TEXT | `open`, `processing`, `accepted`, `denied`, `closed` |
| `created_at` | TEXT | Время создания в UTC |
| `closed_at` | TEXT | Время закрытия |
| `closed_by` | INTEGER | Кто принял решение |
| `reason` | TEXT | Причина решения |
| `log_message_ids` | TEXT | JSON-массив пар `[thread_id, message_id]` для удаления логов вместе с данными |
| `pending_status` | TEXT | Куда переходим, пока статус `processing` |
| `processing_at` | TEXT | Когда заявку захватили, нужно для сверки зависших переходов |

Частичный уникальный индекс не даёт одному человеку иметь две активные заявки на сервере (`status IN ('open','processing') AND user_id != 0`).

### stats (дневная сводка)

| Колонка | Тип | Комментарий |
|---|---|---|
| `id` | INTEGER PK AUTOINCREMENT | |
| `guild_id` | INTEGER | ID сервера |
| `date` | TEXT | День в формате YYYY-MM-DD, уникален вместе с `guild_id` |
| `total_applications` | INTEGER | Решений за день |
| `accepted` | INTEGER | |
| `denied` | INTEGER | |

Персональных данных тут нет, поэтому ретенция и удаление данных её не трогают.

### afk_users

| Колонка | Тип | Комментарий |
|---|---|---|
| `user_id`, `guild_id` | INTEGER | Вместе образуют первичный ключ |
| `afk_reason` | TEXT | Причина, по умолчанию «Отошёл» |
| `afk_since` | TEXT | Начало сессии в UTC |
| `estimated_return` | TEXT | Обещанное время возврата |
| `original_nick` | TEXT | Ник до AFK, чтобы вернуть его обратно |
| `nick_applied` | INTEGER | Ставил ли бот префикс на самом деле |
| `is_afk` | INTEGER | Всегда 1: запись просто удаляется при возврате |

### afk_cooldown

Ключ `(guild_id, mentioner_id, afk_user_id)` и время последнего автоответа. На разных серверах кулдаун независимый. Записи старше суток удаляет фоновая AFK-задача.

### afk_stats

Ключ `(guild_id, user_id)` и три счётчика: количество уходов, суммарные секунды, рекорд сессии.

### bot_state

Key-value для ID объектов, которые бот создал сам (лог-канал и его ветки). Благодаря этому после перезапуска он не плодит дубли.

## Безопасность по умолчанию

- **Упоминания.** Клиент запрещает `@everyone`, `@here` и пинги ролей глобально. Любой текст от пользователя (причина AFK, причина решения) экранируется, служебные пинги формирует только бот и отправляет с точечным списком разрешённых упоминаний.
- **Только ID.** Существующие роли и каналы ищутся строго по ID. Имена в Discord не уникальны, поэтому одноимённая роль не должна получать доступ к тикетам. Заданный, но не найденный ID останавливает запуск.
- **Лог-центр fail closed.** Транскрипты уходят только в канал, прошедший проверку приватности. Никаких запасных вариантов вроде «напишу в первый попавшийся канал» нет, отказ виден в логе.
- **Данные по серверам.** Все таблицы с персональными данными содержат `guild_id`, выборки всегда с ним.

## Принципы, которые стараемся держать

- Тексты и настройки в `config.py`, а не в коде модулей.
- Один модуль - одна зона ответственности.
- Маленькие функции, вложенность до двух уровней.
- Никаких прослоек «на будущее».

## Слабые места, о которых честно

- Часть бизнес-логики живёт в колбэках UI. Когда проект подрастёт, её стоит вынести в сервисный слой.
- SQLite синхронный. Для больших нагрузок понадобится отдельное хранилище.
- Транскрипты, созданные до появления `log_message_ids`, автоматическое удаление не находит. Их придётся чистить руками.
- В `config.py` остались тексты `AFK_VOICE_RETURN_*` от старого поведения «возврат по входу в голосовой канал». Сейчас они не используются.
