# Приватность и жизненный цикл данных

Бот обрабатывает заявки в рамках одного Discord-сервера. Данные тикетов и AFK разделены по `guild_id`, поэтому админы одного сервера не увидят через команды бота данные другого.

## Что хранится

| Что | Где | Зачем |
|---|---|---|
| Ответы формы заявки | SQLite, `tickets.answers` | Рассмотрение кандидата |
| Автор заявки, тип, статус, причина решения | SQLite, `tickets` | История модерации и статистика |
| Переписка тикета | Канал тикета в Discord, транскрипт-файл при закрытии | Контекст решения |
| Итоги решений | Приватный лог-центр | Аудит действий рекрутёров |
| Связь тикета с сообщениями лог-центра | SQLite, `tickets.log_message_ids` | Чтобы удаление данных стирало и вложения |
| AFK-статус и причина | SQLite, `afk_users` | Автоответы и список AFK |
| Исходный ник участника | SQLite, `afk_users.original_nick` | Чтобы вернуть ник после AFK |
| AFK-статистика | SQLite, `afk_stats` | Личная статистика отсутствий |
| Аудит удалений и ретенции | Ветка `🧾-аудит` лог-центра | Кто и когда инициировал удаление |
| Технические логи | `src/app/logs/bot.log` | Диагностика |

В обычные логи не попадают ответы анкет, содержимое транскриптов и токен. Там только технические события: какой тикет создан, какая ошибка произошла, ID объектов.

## Что видит пользователь

Панель `!famqcore` в описании предупреждает: отправляя заявку, человек соглашается, что ответы формы и сообщения тикета сохраняются для рассмотрения администрацией этого сервера, а удаление можно запросить у администратора.

## Кто имеет доступ

- Канал тикета видят заявитель, бот и настроенные стафф-роли.
- Лог-центр приватный: закрыт для `@everyone`, открыт боту и стафф-ролям из `.env`. Готовый канал из `LOG_CHANNEL_ID` проходит ту же проверку, и если он открыт лишним людям, бот туда писать не станет, а в production вообще не запустится.
- `!stats`, `!history` и `!delete_user_data` доступны только администраторам Discord-сервера.
- Роли с правом Administrator видят любой канал средствами самого Discord, это вне контроля бота.

## Удаление данных участника

```text
!delete_user_data @user
```

Команда необратима и требует подтверждения кнопкой, причём кнопки слушают только того админа, который вызвал команду. Если подтверждения нет 60 секунд, кнопки снимаются и бот сообщает, что ничего не удалено. Работает в рамках текущего сервера.

| Что | Что с этим происходит |
|---|---|
| Открытый тикет | Канал удаляется вместе со всей перепиской |
| Записи тикетов | Анонимизируются: `user_id` становится `0`, имя `deleted-user`, ответы формы и причина решения стираются, активные тикеты закрываются |
| Сообщения лог-центра по этим тикетам | Удаляются вместе с транскриптами по сохранённой связи `log_message_ids` |
| Активный AFK | Удаляется, префикс `[AFK]` снимается, возвращается исходный ник |
| AFK-статистика и кулдауны | Удаляются |
| Дневная сводка решений | Остаётся, персональных данных в ней нет |
| Аудит | В ветку `🧾-аудит` пишется запись: ID админа, ID участника и счётчики удалённого, без самих данных |
| Бэкапы | См. раздел ниже |

После анонимизации человек может подать новую заявку, обезличенные записи ему не мешают.

Чего бот сделать не может: удалить сообщения участника в обычных каналах сервера, чужие скриншоты и выгрузки. Это уже задача администраторов сервера.

Если удаление упало на середине, бот честно сообщит об ошибке и даст код для поиска в логе. Команду можно повторить после устранения причины.

## Сроки хранения

Фоновая задача запускается каждые `RETENTION_CHECK_SECONDS` (по умолчанию раз в сутки) и удаляет заявки старше `TICKET_RETENTION_DAYS` (по умолчанию 180 дней):

- закрытые считаются по дате закрытия, заброшенные активные по дате создания;
- записи тикетов удаляются из базы полностью;
- каналы заброшенных тикетов удаляются, если они ещё существуют;
- привязанные сообщения лог-центра с транскриптами тоже удаляются;
- итог каждого прохода пишется в ветку `🧾-аудит`.

Из этого следует важная мелочь: счётчики `!stats` (всего, принято, отклонено) считаются по живым записям тикетов, то есть отражают окно хранения. Дневная сводка в таблице `stats` персональных данных не содержит и хранится постоянно.

Транскрипты, отправленные до появления связи `log_message_ids`, автоматическая очистка найти не может. Это известное исключение, такие сообщения удаляются вручную.

Разумная политика для боевого сервера:

- открытые тикеты живут до решения или ручного закрытия;
- закрытые тикеты и транскрипты - `TICKET_RETENTION_DAYS`, если правила сервера не требуют меньше;
- технические логи - текущая ротация 3 файла по 5 МБ;
- бэкапы SQLite - последние 14 ежедневных копий;
- таблица `afk_cooldown` чистится сама, записи старше суток удаляет фоновая AFK-задача.

## Бэкапы

Бэкап `database.db` это копия персональных данных со всеми вытекающими:

- доступ к бэкапам должен быть у тех же людей, что имеют доступ к лог-центру;
- держите ограниченное количество копий и ротируйте их автоматически;
- удалённые данные исчезают из бэкапов по мере ротации, именно это и обещает `!delete_user_data`, мгновенного стирания в архивах не бывает;
- если восстановиться из старого бэкапа, вернутся и уже удалённые данные, удаление придётся повторить.

Пока автоматическая ротация не настроена, делайте ручной бэкап по инструкции из [deployment.md](deployment.md) и сами удаляйте старые копии.

## Старые данные и миграции

Записи, созданные до появления `guild_id`, привязать к конкретному серверу невозможно. Миграция переносит их в служебный `guild_id = 0`. Новые записи всегда создаются с реальным ID сервера.
