# Приватность и жизненный цикл данных

Бот обрабатывает заявки внутри конкретного Discord-сервера. Начиная с текущей схемы БД, персональные данные тикетов и AFK-статистики изолированы по `guild_id`: администраторы одного сервера не получают выборки другого сервера через команды бота.

## Что сохраняется

| Категория | Где хранится | Для чего |
|-----------|--------------|----------|
| Ответы формы заявки | SQLite, таблица `tickets.answers` | Рассмотрение кандидата рекрутёрами |
| Автор заявки, тип, статус, причина решения | SQLite, таблица `tickets` | История модерации и статистика |
| Сообщения приватного тикета | Discord-канал тикета, transcript-файл при закрытии/решении | Проверка контекста решения |
| Итоги решений | Приватный лог-центр Discord | Аудит действий рекрутёров |
| Связь тикета с сообщениями лог-центра | SQLite, `tickets.log_message_ids` | Чтобы удаление данных стирало вложения |
| AFK-статус и причина | SQLite, таблица `afk_users` | Автоответы и отображение списка AFK |
| AFK-статистика | SQLite, таблица `afk_stats` | Личная статистика отсутствий на сервере |
| Минимальный аудит удалений | Приватная ветка `🧾-аудит` лог-центра | Кто и когда инициировал удаление данных |
| Технические логи | `logs/bot.log` | Диагностика ошибок |

В обычные application-логи не пишутся полные ответы анкет и transcript-содержимое. Логи содержат технические события: создание тикета, ошибки, ID/имена объектов Discord.

## Уведомление пользователя

Панель `!famqcore` показывает предупреждение: отправляя заявку, пользователь соглашается на сохранение ответов формы и сообщений тикета для рассмотрения администрацией текущего Discord-сервера.

## Доступ

- Тикет видят заявитель, бот и настроенные стафф-роли.
- Лог-центр создаётся приватным: закрыт для `@everyone`, открыт боту и стафф-ролям из `.env`. Существующий канал из `.env` проходит ту же проверку приватности: если `@everyone` видит канал или доступ открыт посторонним ролям/участникам, бот отказывается туда писать (fail closed), а в production — не запускается.
- Команды `!stats`, `!history` и `!delete_user_data` доступны только администраторам Discord-сервера.

## Удаление и анонимизация

Администратор сервера может выполнить:

```text
!delete_user_data @user
```

Команда необратима и **требует подтверждения кнопкой** (кнопки реагируют только на вызвавшего её администратора). Команда работает в рамках текущего `guild_id` и выполняет именно то, что объявлено в тексте подтверждения:

| Что | Действие |
|-----|----------|
| Открытый тикет | Канал удаляется вместе со всей перепиской и доступом |
| Записи тикетов | Анонимизируются: `user_id` → `0`, имя → `deleted-user`, ответы формы стираются, причина решения очищается; открытые становятся закрытыми |
| Сообщения лог-центра по этим тикетам | Удаляются вместе с транскриптами-вложениями (по сохранённой связи `log_message_ids`) |
| Активный AFK-статус | Удаляется; префикс `[AFK]` снимается с ника, исходный ник восстанавливается |
| AFK-статистика и кулдауны автоответов | Удаляются |
| Агрегированная статистика решений | Остаётся: персональных данных в ней нет |
| Аудит | В ветку `🧾-аудит` пишется запись: ID администратора, ID субъекта данных и счётчики обработанных объектов — без самих персональных данных |
| Резервные бэкапы | См. раздел про бэкапы |

После анонимизации человек может подать новую заявку — старые обезличенные записи не блокируют её.

Чего бот сделать не может: сообщения, которые участник сам оставил в общих каналах сервера, скриншоты и выгрузки, сделанные другими участниками. Это удаляется процедурами администратора сервера.

## Ретенция

Фоновая задача ретенции запускается каждые `RETENTION_CHECK_SECONDS` (по умолчанию сутки) и удаляет заявки старше `TICKET_RETENTION_DAYS` (по умолчанию 180 дней):

- закрытые — по дате закрытия, заброшенные открытые — по дате создания;
- записи тикетов удаляются из БД полностью;
- каналы заброшенных открытых тикетов удаляются, если ещё существуют;
- привязанные сообщения лог-центра (транскрипты) удаляются;
- результат каждого прохода фиксируется в ветке `🧾-аудит`.

Следствие: сводные счётчики `!stats` (всего/принято/отклонено) считаются по живым записям тикетов и отражают окно хранения; дневная агрегация `stats` без персональных данных хранится постоянно. Транскрипты, созданные до появления связи `log_message_ids`, ретенция найти не может — это объявленное исключение; удаляйте их вручную при необходимости.

Рекомендуемая политика для production:

- открытые тикеты — до решения или ручного закрытия;
- закрытые тикеты и transcript-файлы — `TICKET_RETENTION_DAYS` (по умолчанию 180 дней), если правила сервера не требуют меньше;
- технические логи — текущая ротация `3 x 5 МБ`;
- бэкапы SQLite — хранить последние 14 ежедневных копий;
- записи `afk_cooldown` очищаются автоматически фоновым циклом, чтобы таблица не росла бесконечно.

## Бэкапы и удаление

Бэкапы `database.db` — это копии персональных данных со всеми обязательствами:

- доступ к бэкапам должен быть ограничен теми же администраторами, что имеют доступ к лог-центру;
- храните ограниченный срок (рекомендация — 14 ежедневных копий) и ротируйте автоматически;
- удалённые из живой базы данные физически исчезают из бэкапов по мере их ротации — именно это (а не мгновенное стирание в архивах) и обещает команда `!delete_user_data`;
- при восстановлении из бэкапа вернутся и данные, уже удалённые на момент создания других копий — удаление придётся повторить.

Настройте автоматическую ротацию бэкапов в своей инфраструктуре. До её настройки используйте ручной бэкап из [руководства по деплою](deployment.md) и удаляйте старые копии по этой политике.

## Миграции и старые данные

Старые записи, созданные до появления `guild_id`, невозможно надёжно привязать к серверу. Миграция переносит их в служебный `guild_id = 0`. Новые записи всегда создаются с реальным ID сервера Discord.
